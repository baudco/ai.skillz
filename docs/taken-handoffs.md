# Store-native work handoffs

The task is the handoff; the reply is its locator.

## Authoritative location and write authority

For repository work handed to another human or agent, use an identified
task subtree in the selected Taken store as the authoritative handoff.
Put the objective, context, unresolved concerns, execution steps,
verification and expected handback there. Do not create a separate
instruction document unless the human explicitly asks for one.

Keep plans, source documents, logs, snapshots and review reports as
linked evidence when useful. They must not be the only place containing
instructions required to carry out the handed-off work. Existing
historical references need not be moved or deleted.

Resolve the source registration and task ID before saving. Prefer source
ID plus Org task ID; provide the current resolved path for navigation.
Honor existing scoped write authorization. Without it, render a complete
Org task-subtree proposal and state that it is not saved. A request to
read or review never silently becomes permission to mutate a store.
Use the deployed Taken guarded writer for authorized changes. Preserve
existing task/checkbox states; new proposed work uses TODO and unchecked
checkboxes. Do not overwrite another worker's identity or task scope.

## Human-readable task structure

Start with a short objective and immediate next action. Put detailed
instructions beneath named child headings such as Context, Concerns,
Execution, Verification and Handback. Use one identified work task per
bounded assignment; grouping headings need not carry task states.
Link existing canonical concern tasks rather than copying their ownership.
Retain snapshots only when they preserve evidence behind a decision.

## Producer response

When reporting a saved handoff, lead with the navigable authoritative
store/task location, stable source and task IDs, full headline path,
and saved/committed status. Identify that task as the worker's entry
point. Mention supporting artifacts afterward. For an unsaved proposal,
report that status explicitly; never invent a locator or saved receipt.

A complete review body can remain findings-first inside its own output
contract. Its task-first handoff locator is a separate cover note. Private
review-context and commit-plan artifacts remain operational evidence,
not substitutes for the task's human-readable work instructions.

## Receiving worker

Given a source/store and task ID, read the complete task subtree,
applicable parent context and explicitly linked prerequisite tasks before
acting. Follow the current authorized assignment, not every TODO in the
store. Reading a task alone is not authorization to execute its work.

Treat linked historical evidence as evidence, not an additional command
queue. Resolve contradictions against the latest human direction in the
task and current conversation; current explicit instructions prevail.
If unresolved contradictions change scope, record them and clarify rather
than silently choosing a historical plan or expanding the assignment.

## Review obligations and handback

Keep unresolved human questions as explicit review obligations. For each,
identify evidence, findings and proposed disposition. Passing tests does
not settle an architecture/history concern or authorize acceptance.
Do not silently dismiss or defer a concern; link its canonical task.

Return findings against the originating task ID. With write authority,
reconcile concise results, blockers, decisions and next actions into that
same task using the guarded writer. Keep detailed reports as linked
evidence. Without write authority, return a scoped update proposal.
A completed execution, clean tests or a commit never changes human-owned
acceptance markers automatically.
